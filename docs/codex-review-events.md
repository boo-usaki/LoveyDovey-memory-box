# 「事件」功能唯讀審查

審查基準：`main` commit `25a911d8c1bb408b658ebeb65388c2799c47511b`  
審查範圍：`index.html` 的 Events／匯入／刪除／GitHub Gist／Claude 同步，以及 `README.md`、`AGENT.md` 的事件說明。  
本分支只新增這份審查報告，沒有修改程式碼。

## 結論先講

事件的主要互動方向是對的：自動接續編號、欄位快滿時停下詢問、支援不用代號，以及「接續 app 裡既有事件欄」都有清楚的產品意圖。不過目前有幾個資料安全問題應先處理，尤其是：**備份沒有事件、等待使用者決定的溢位佇列沒有同步、事件本體和欄位中繼資料採不同同步方式而可能脫鉤**。這三項可能讓使用者以為資料仍在，實際上卻無法從畫面找回或繼續處理。

## P1｜高嚴重度

### 1. 「備份」完全沒有包含事件，清除後無法還原

- **位置**：`index.html:2413-2424`（`backupJSON`）；`index.html:739-750`（備份與「清除全部記憶與事件」介面）；README「同步與備份」。
- **會發生什麼事**：`backupJSON()` 只輸出 `state.memories`，沒有 `events`、事件欄 `companions[].ev`、事件格式、整理範圍或尚待決定的溢位內容。使用者看到「備份」後，很合理地會以為事件也已備份；若接著按「清除全部記憶與事件」、清除瀏覽器資料，或同步資料出問題，事件無法由該備份復原。
- **建議**：把備份升級成有版本號的完整資料包，至少包含 `memories`、`events`、`companions`、`settings`、`evPending`、`meta`，並提供對應的完整還原流程。若暫時不做，按鈕和說明必須明寫「只備份記憶，不含事件」，且「清除全部」前另行警告事件沒有備份。

### 2. 「下一則放不下」的等待狀態只存在當前瀏覽器，換裝置後整段待處理事件會消失

- **位置**：`index.html:1726-1737`（`state.evPending`）；`index.html:1060-1095`（只有 localStorage 保存）；`index.html:2155-2156`（Gist payload 沒有 `evPending`）；`index.html:2452-2562`（Claude 同步也沒有 pending collection／欄位）。
- **會發生什麼事**：一次匯入如果前幾則已放入、下一則剛好放不下，前幾則會立即存檔並推進部分進度，剩下的 queue 只留在這台裝置的 localStorage。此時改用手機、另一台電腦，或在 Claude 裡換裝置開啟，使用者看不到「改短／開新欄」的問題，也拿不回後面尚未放入的事件。這直接破壞「一定先問使用者」的需求。
- **建議**：要嘛把 pending 當成正式同步資料（含 stable id、建立時間、來源範圍、完整 queue），在 Gist 與 Claude 都同步；要嘛改成交易式流程，在使用者作出選擇前不要提交這批匯入的任何事件與進度。所有裝置都應顯示同一個待決定狀態。

### 3. 同步時事件本體與事件欄中繼資料可能分離，造成「資料還在但畫面看不到」

- **位置**：`index.html:1637-1672`（欄號、開始／結束日期存在 `companions[].ev`）；`index.html:2173-2218`（Gist 合併只在整個 `ev` 缺少時補上，不逐類別／逐欄合併）；`index.html:2480-2487`、`2563-2575`（Claude 將整份 `companions` 寫入／替換）；`index.html:2543-2562`（事件本體另存在 collection）。
- **會發生什麼事**：兩台裝置同時整理不同類別、不同事件欄，或一台裝置帶著較舊的 companion 設定重新連線時，事件 document 可能都保留，但 `slots`、`base`、`baseIdx`、`from/to` 等欄位中繼資料被另一台的整個 `ev` 物件覆蓋。`renderEventList()` 是從 slots 開始畫畫面，因此事件可能變成 orphan：同步裡有資料，頁面卻沒有對應欄可顯示；接續編號也可能倒退。
- **建議**：不要把整個 `companions`／`ev` 當單一 last-writer-wins 文件。把事件欄中繼資料正規化成 `companion + category + slot` 的獨立紀錄，附 `updatedAt` 與 tombstone；或至少在 Gist／Claude 兩端都按 companion、category、slot 深度合併並處理刪除。合併後要驗證每一則 live event 都有對應 slot。

### 4. 刪除／改名事件類別代號會讓既有事件失去入口

- **位置**：README `74` 行（類別可自行增加或刪除）；`index.html:1539-1551`（類別清單）；`index.html:1637-1645`（資料以 code 為 key）；`index.html:1667-1669`、`1867-1889`（畫面只渲染目前清單中的類別）。
- **會發生什麼事**：使用者從事件格式刪掉 FIR、把 FIR 改名成 REL，或不小心改錯代號，原本 `cat: FIR` 的事件與 `ev.FIR.slots` 仍在資料裡，但 UI 不再提供 FIR 頁籤，使用者會以為事件消失。agent API 若傳入不存在的代號，也能建立 UI 選不到的隱藏資料。
- **建議**：有資料的代號不得直接刪除／改名；先顯示影響筆數，讓使用者選「保留封存」「搬到另一類」「確認刪除」。代號改名要做原子 migration，同時搬移 events、slots、range 與 pending。`setEventRange`／`eventPrompt`／`importEvents` 遇到未知 category 應回傳錯誤，不要靜默建立。

### 5. 刪除最後一則事件後，下一次會重用相同編號

- **位置**：`index.html:1537`（`liveEvents` 排除 deleted）；`index.html:1649-1651`（`nextIdx` 只看 live events）；`index.html:1980-1983`（刪除只設 `deleted = true`）。
- **會發生什麼事**：例如 `[FIR-05-03]` 已複製到卿卿我我後，在記憶匣裡刪除；下一次新增時，`nextIdx` 看不到 tombstone，會再次產生 `[FIR-05-03]`。外部 app 可能同時存在兩個相同代號，後續接續與人工核對都會混亂。
- **建議**：每欄保存單調遞增的 `lastIdx`／high-water mark，刪除不得降低；或計算時把 tombstone 也納入。若使用者真的要回收編號，另做明確的「重新編號」工具並警告外部 app 的既有內容不會自動更新。

### 6. 空欄與 agent API 可以繞過每欄 2000 字上限

- **位置**：`index.html:1700-1719`（只有 `used` 非零才檢查 overflow）；`index.html:1769-1785`（`fit` 設 `force = true`）；`index.html:1907-1913`（只有畫面按鈕會先停用過長內容）。
- **會發生什麼事**：若單一事件本身就超過欄上限，空欄因 `used === 0` 會直接塞入；選「開新欄」也一樣超標。agent 直接呼叫 `resolveEventOverflow("fit", text)` 時，無論文字是否真的小於 `pending.room`，`force` 都會略過檢查。結果頁面可能產生超過 2000 字的事件欄，且沒有再次詢問。
- **建議**：永遠檢查 `need > lim`，空欄也不例外；`fit` 解析後重新以 `eventText()` 計算，只有 `need <= room` 才接受。過長時保留原 pending，不改資料，回傳實際需要／剩餘字數。`itemLimit` 也應在匯入時驗證，而不只是顯示紅字。

### 7. Claude「清除全部」的遠端刪除失敗被完全吞掉，資料可能重新出現（不確定：需 Claude Artifact 實機驗證）

- **位置**：`index.html:2426-2430`（立即顯示清除完成）；`index.html:2468-2479`（remote delete 的錯誤 `.catch(() => {})`）；`index.html:2534-2562`（snapshot 會再把遠端資料載回）。
- **會發生什麼事**：若 Claude db 刪除因離線、權限或暫時錯誤失敗，UI 仍顯示已清除；遠端 document 仍在，後續 snapshot 或重新開頁可能讓記憶／事件重新出現。因錯誤被吞掉，使用者無從知道清除其實沒有完成。
- **建議**：遠端清除要有可觀察的完成結果；使用 tombstone／clear epoch 或 batch transaction，全部成功後才顯示完成。失敗要保留本機復原資訊並顯示「本機已隱藏、Claude 尚未刪除」。此項依賴 `window.claude` 的實際 db 行為，建議在 Claude Artifact 內斷網／撤權測一次。

## P2｜中嚴重度

### 8. 重複判斷既可能覆蓋不同事件，也無法防止跨裝置重複匯入

- **位置**：`index.html:1704-1709`（只用 companion + category + keywords + date 判定同一則）；`index.html:2176-2194`（Gist 只按隨機 id 合併）。
- **會發生什麼事**：同一天兩件事都叫「吵架、和好」時，後匯入者會覆蓋前一件；反過來，同一份 AI 回覆若在兩台離線裝置各匯入一次，會生成不同隨機 id，Gist 合併後保留兩份。只要 AI 微調關鍵字或日期，也會重複新增。
- **建議**：建立穩定的 import fingerprint（例如 companion、category、事件日期、標準化內容的 hash），把「完全相同」「疑似相同」「確定不同」分開處理。碰到相同日期＋關鍵字但內容不同時不要直接覆蓋，應提示使用者選更新或保留兩則。

### 9. 「接續 app 既有事件欄」可建立兩個相同欄號

- **位置**：`index.html:2007-2029`，尤其 `2018-2022`。
- **會發生什麼事**：如果使用者輸入一個本機已經有事件的欄號，舊 slot 因為有 items 會被保留，接著又 `push` 一個同樣 `no` 的新 slot。畫面可能出現兩張 `[FIR-05]`，相同事件重複顯示，`openSlot()` 與 `nextIdx()` 也可能選到非預期的那一張。
- **建議**：儲存前檢查 `companion + category + slotNo` 唯一性。已有該欄時，明確提供「更新既有欄的 app 內文」或「取消」，不要再新增同號 slot；更新時也要驗證 base 內的最後編號不小於既有 high-water mark。

### 10. 匯入內容可靜默寫到另一位伴侶或另一類事件

- **位置**：`index.html:1690-1692`（接受 JSON 裡的 companion/category）；`index.html:1749-1758`（依回覆內容分組並寫入）；`index.html:1761`（切換 current）。
- **會發生什麼事**：使用者正在 A 的 FIR 頁面，卻貼到 AI 回覆中的 `companion: B` 或 `category: EV`，頁面不會警告，而是直接寫進 B／EV；若名字是 AI 拼錯的，還會建立新的伴侶紀錄。一般使用者只看到「匯入成功」，容易以為資料不見。
- **建議**：互動匯入預設鎖定目前選取的 companion/category；回覆不一致時先列出差異並請確認。agent API 若要支援多伴侶／多類別批次，應加明確的 `allowMixed: true`，而不是預設接受。

### 11. pending 會鎖住所有新匯入，但切走後沒有全域入口可回去處理

- **位置**：`index.html:1740-1744`（任何 pending 都阻擋新匯入）；`index.html:1873-1875`（只有在原伴侶畫面顯示卡片）。
- **會發生什麼事**：使用者切到別的伴侶後再匯入，只看到「還有一則事件在等妳決定」，卻不知道是哪位伴侶、哪一類，也沒有按鈕帶回去；手機上尤其容易以為流程壞掉。
- **建議**：在所有頁面顯示固定的 pending banner，寫明 companion、category、column、事件關鍵字，並提供「回去處理」。API error 也要回傳／顯示這些資訊。

### 12. 日期範圍與 AI 回傳日期沒有驗證，可能錯誤推進進度

- **位置**：`index.html:1794-1796`（只在 prompt 說明範圍）；`index.html:2115-2118`、`2337-2342`（未檢查 from <= to）；`index.html:1690-1692`、`1720-1723`（匯入後直接依 date 推進）。
- **會發生什麼事**：使用者可選到「從晚於到」；AI 也可能回傳範圍外或格式錯誤的日期。頁面仍照收，並可能把下次起點往後推，讓後續對話被跳過。
- **建議**：設定範圍時驗證順序；匯入前把每則 date 與範圍比對，範圍外、空日期、`fields.時間` 與 `date` 不一致都列為需確認，不應自動推進 `r.from`。

### 13. `buildEventPrompt` 的防重資訊太弱，常見關鍵字會讓 AI 判斷錯誤

- **位置**：`index.html:1797-1816`。
- **會發生什麼事**：指令只列最後 30 則的「關鍵字」，沒有日期、事件摘要、欄號，也沒有 app 既有欄 `slot.base` 的事件。像「吵架、和好」「生日」「散步」這種關鍵字可能代表不同事件，AI 可能誤以為已整理而漏掉；超過 30 則或只存在 base 的舊事件則可能重複寫。
- **建議**：傳給 AI 的已整理索引至少包含 `日期｜關鍵字｜極短摘要／fingerprint`，並納入目前 base；明說「相同關鍵字不代表同一事件，以日期與內容判斷」。若索引太長，按本次日期範圍篩選，而不是固定取最後 30 則。

### 14. 不用代號時，五個長類別按鈕在手機上可能水平溢出

- **位置**：`index.html:110-112`（`.seg` 是不換行的 inline-flex）；`index.html:277-280`（事件類別沒有捲動／換行）；`index.html:258-274`、`313-316`（手機規則未處理 `.ev-cats`）。
- **會發生什麼事**：使用代號時 FIR／EV 尚短；切成「不用代號」後會顯示「關係重大進展、劇情進展、日常紀錄……」，五個按鈕排在同一行，窄螢幕可能被切掉且無明顯可捲動提示。
- **建議**：手機版讓 `.ev-cats` 使用 `max-width: 100%; overflow-x: auto;` 並保留滑動提示，或改成可換行 chips／下拉選單；實機驗證 320、375、390px。

### 15. 精簡結果的解析過度寬鬆，AI 多回一句說明就可能被當成事件標題

- **位置**：`index.html:1609-1634`（`firstIsHead` 會接受第一行任意文字）；`index.html:1769-1776`（未先 `stripFence` 就覆寫 pending 事件）。
- **會發生什麼事**：AI 若回傳 ``` code fence、或先寫「以下是精簡後內容」，第一行可能被當成關鍵字，欄位解析為空，然後原 pending 事件被改壞並強制放入。
- **建議**：先 `stripFence`，再要求第一行必須符合目前的 head template／代號格式；解析失敗時不要改 `e`，保留原 pending 並回傳可修正的錯誤。

## P3｜可用性與維護性

### 16. 事件頁仍顯示「查看／修改」，但事件指令其實是唯讀

- **位置**：`index.html:486-487`；`index.html:1343-1351`。
- **會發生什麼事**：同一顆按鈕在記憶模式真的能修改 prompt，在事件模式卻把 textarea 設為 read-only 並隱藏編輯；一般使用者會以為功能故障。
- **建議**：事件模式把按鈕改成「查看指令」，並在旁邊提供「修改事件規則」直接跳到事件格式區。

### 17. 建議補一組不依賴 DOM 的事件回歸測試

- **位置**：整個 repo；目前只有單一 HTML，沒有事件資料模型／同步合併的自動測試。
- **會發生什麼事**：編號、tombstone、overflow queue、跨欄、Gist merge、Claude merge 都互相影響，只靠手動點擊很容易修 A 壞 B。
- **建議**：把 `nextIdx`、`placeQueue`、`mergeRemote`、category migration、backup/restore 拆成純函式，至少覆蓋：刪除最後一則後再新增、同日同關鍵字兩事件、跨裝置重複匯入、pending 換裝置、單則大於欄上限、同欄號接續、類別改名、兩裝置同時改不同 category。

## `buildEventPrompt` 文字本身的補強建議

除了第 13 點，建議把下面幾句直接寫進指令，能顯著降低 AI 自行腦補或日期漂移：

1. `date` 必須是「事件實際發生日期」，不是整理日或檔案日期；無法從對話判斷時留空，不得猜測。
2. `fields.時間` 與 `date` 的日期必須一致；只有時段可以用「晚上／深夜」等自然文字。
3. 同一天可以有多件事件；不要只因關鍵字相似就合併，只有同一件事的連續對話才合併。
4. 不要輸出伴侶／類別以外的值；這次固定是指定 companion 與 category。
5. `細節` 每一項只放一個事實或一句關鍵對話；沒有證據的心理、承諾、關係定義不得推測。
6. 若內容可能屬於兩個類別，只收進本次指定類別最符合的事件，不要同一事件重複輸出兩次。
